revert: timeout 45 was overfitting, and copy_ratio is an unmeasured assumption

The operator called it: 'overfit, right?' The ledger agrees.

timeout_minutes 180 -> 45 was set from one observation (five dead positions
sitting within +/-1%). Hold-bucket returns say the opposite:

  <15m     n=1  -17.2%
  45-90m   n=3  -14.9%
  90-180m  n=8   +9.8%  <- the ONLY positive-expectancy bucket
  >180m    n=48  -1.8%  (53/60 exits are TIMEOUT -- a selection problem, not
                        a hold-duration problem; shortening the timeout was
                        treating the symptom)

Reverted to 180, with the numbers written next to the knob so nobody re-tunes
it from a hunch again. The 53 TIMEOUT exits mean the funnel is not selecting
momentum; that is an edge question for the replay engine, not a timeout
question.

copy_ratio 0.5 stays as a mechanism but is now labelled in config as an
UNVALIDATED ASSUMPTION: of D's 36 attributable closes, ZERO had a source
signal above 5k USD. The two small buckets lean the right way (40% vs 23% win
rate) but n=10 vs n=26 cannot carry a parameter. ARBITER validates it when
shadow marks accumulate.

What is NOT reverted: the adaptive-floor fix. That was a logic fix, not a
parameter fit -- when vetoes reject 67% of candidates, decaying the score
floor changes no outcome; that is a structural fact about the reject
distribution, not a fitted value.
