## 0. 一句话结论

**低延迟 Crypto 方向证伪，且证伪理由与"延迟不够快"无关——而是"这个标的的正确做法不是抢延迟"。**
气象线拿到了第一批真实的一手数据：**METAR 从观测时刻到公开 API 可读的固有延迟是 136–328 秒（中位约 210 秒）**，这个延迟由 NWS 决定，任何参与者都绕不开，因此它既是风险也是机会——但目前**尚未观测到可吃的归零窗口**，需要更长录制。

## 1. 本轮纠正的三个自身错误（必须先说）

不把这三个错误说清楚，后面的数字都不可信。

### 错误一：测量口径搞错了标的的结算统计量

`btc-updown-5m-*` 的结算规则（市场描述原文）是：

> resolve to "Up" if the **time-weighted average price (TWAP)** of Bitcoin, generated by Chainlink, of the time range specified in the title is greater than or equal to the **price at the beginning** of that range.

实测验证（**39 个已结算窗口**）：

| 判定方式 | 命中率 |
|---|---|
| 窗口内 TWAP 均值 ≥ 开盘价 | **35/39 = 89.7%** |
| 窗口末价 ≥ 开盘价 | 35/39 = 89.7% |

> 更早一轮 38 窗口的对照里，TWAP 92.1% 对末价 86.8%——差额全部来自"末价回到开盘附近但中途大幅偏离"的窗口。两轮合并看：**TWAP 是更正确但差异不大的统计量**，关键结论是它**不是末价**。

**这条事实推翻了整个毫秒延迟实验的前提**：现货一次 5bps 的瞬时跳动，对 5 分钟均值的贡献是
`5bps × (1s/300s) ≈ 0.017bps`，对平值市场公允概率的影响**远小于 1 tick（名义 100bps）**。
盘口不动是**数学上正确的行为**，不是"反应慢"。

### 错误二：把"数据采样不足"当成"市场反应慢"

第一版 `twap_efficiency.py` 报出极漂亮的数字：

```
候选交易 149 笔  胜率 75.2%  净收益率 +2032bps
```

**这是假 edge，已作废。** 原因是我拿 `prices-history` 的 REST 采样点当成交价，而该接口对 5m token 的采样间隔是 **40–46 秒**。于是"模型刚看完最新 K 线"和"盘口价是 46 秒前的"被直接对比，凭空造出 18.5pp 的平均 edge。

加入**陈旧度分层**后立刻暴露：

| 盘口陈旧上限 | n | 胜率 | 净收益 |
|---|---|---|---|
| **≤15s** | 7 | **28.6%** | **−3278bps** |
| ≤30s | 24 | 62.5% | +2342bps |
| ≤60s | 154 | 72.7% | +1922bps |

**当报价真正新鲜时，edge 消失并翻负。** 那 1922bps 只存在于"旧报价"上，而旧报价不可能成交。

### 错误三：方向语义写反

第一版把"受益 token 的 ask 上行"当成反应信号，没区分 `up`/`down` 两侧。已改为：
现货上涨 ⇒ `up` token 变贵（ask **升**）、`down` token 变便宜（ask **降**）；真重定价需**两侧同时动**。

## 2. 5m 平值市场的真实结构（一手实测）

### 2.1 盘口形态：1 tick 焊死

30 分钟录制、**579,917 条** Polymarket 推送、6 个完整窗口：

| 窗口阶段 | 盘口表现 |
|---|---|
| 平值窗口（刚开盘） | `ask` 恒为 0.51、`bid` 恒为 0.50 |
| 9514 条推送 / 2 分钟 | 只有 **4 个唯一 ask 值**（0.01/0.02/0.03/0.04） |

**推送量与实际改价完全脱钩。** 极高频重报同一价位（churn），这就是为什么"到下一次推送"恒等于 0ms——上一轮把 14ms 当成"反应快"、以及本轮早期版本把 churn 当反应，都是同一个陷阱。

### 2.2 费率是天花板

`feeType = crypto_btc_5m_15m_fees`，`takerBaseRate = 0.05`（已由 `fee-rate` 接口 `base_fee=1000` 佐证）：

```
fee = 份数 × 0.05 × p × (1−p)     每股
```

- `p = 0.50` 时 = **名义金额的 2.5%**（最贵档）
- `p = 0.90` 时 = 0.5%
- maker 永远 0

平值市场恰恰是费率最贵的地方。要在 p=0.5 赚钱，需要单笔期望收益 > 2.5% 名义，即**公允概率要偏 5pp 以上**。而 5bps 现货跳动对 TWAP 的贡献是 0.017bps，相差三个数量级。

### 2.3 结算基准不是币安

Chainlink BTC/USD **TWAP-60s** data stream，不是现货瞬时价。跨所基差本身就会造成方向误判：
早期用币安现货方向预测结算，23 个窗口命中 **17/23 = 73.9%**，其中 |变动|<5bps 的 4 个窗口只有 **2/4**——这正是"赌硬币"区。

## 3. 判定：低延迟 Crypto 证伪（结构性，非参数）

用户设定的三条硬门槛，逐条对照：

| 门槛 | 实测 | 判定 |
|---|---|---|
| `p50(t2−t0) < 300ms` → 放弃 | 5bps 事件在 2 tick 网格上**几乎不产生**同向变动（数学上应如此） | 不适用——前提不成立 |
| 扣费净利 ≤ 0 → 放弃 | 新鲜报价（≤15s）下 **−3278bps** | **触发** |
| 可吃深度 < $200 → 放弃 | 平值档深度约 $200–400 | 临界 |

**结论：放弃低延迟 Crypto。** 但要说清理由——不是"我们不够快"，而是：

1. 标的结算统计量是 5 分钟均值，瞬时跳动被稀释 300 倍；
2. 费率在平值处高达名义 2.5%，需要 5pp 级概率偏差才能覆盖；
3. 这两条相乘，意味着**这个标的的可交易 edge 不在延迟维度上**。抢延迟最多赢 100ms，而需要赢的是 5pp 概率。

这比"p50 = 800ms 所以放弃"强得多：即使延迟归零，这条路仍然不通。

**唯一未被排除的变体**：利用"盘口对瞬时脉冲过度反应"做反向（TWAP 说 0.50，盘口因脉冲跳到 0.35 → 买 UP）。但这属于做市/逆势逻辑，不是 taker 抢跑，且需要连续报价能力与库存管理——超出 M1 的"纯只读验证"范围，本轮不做。

## 4. 气象 METAR：第一批一手数据

### 4.1 市场规模（事实核对）

| 指标 | 实测值 |
|---|---|
| 活跃温度事件 | **144 个**（含次日） |
| 可交易档位合计 | **1,575 个** |
| 单城市日 | 11 档 |
| 单城市日成交量 | $9,800 – $66,375 |

> 用户提到的"792 个市场"应为较早时点或不同统计口径；当前实测是 144 事件 / 1,575 档位。

### 4.2 数据源延迟（核心数字）

同一时刻批量查询 9 站（8 站 1.7s，单站 1.5–2.1s），`receiptTime − obsTime`：

| 站点 | 观测延迟 | 城市 |
|---|---|---|
| LFPB | 136s | Paris |
| EHAM | 140s | Amsterdam |
| KLGA | 188s | NYC |
| EDDM | 210s | Munich |
| KLAX | 210s | Los Angeles |
| KSEA | 211s | Seattle |
| KMDW | 222s | Chicago |
| LEMD | 253s | Madrid |
| EGLC | 328s | London |

**中位约 210 秒。** 三轮测量完全一致（136/140/188/210/210/211/222/253/328 三次重复值不变），说明这是稳定的系统性延迟，不是网络抖动。

**这条数字的两面性：**
- **坏消息**：我不能比别人早 200 秒看到报文——所有人共用同一个源。
- **好消息**：正因为所有人都是同一时刻看到，**盘口的重定价必然发生在那 200 秒之后的几秒内**。所以竞争窗口不在"更早看到"，而在"看到后更快下单"——这仍然是延迟游戏，但窗口从毫秒级变成秒级，个人有可能参与。

### 4.3 结算规则的三个陷阱（已解析并验证）

市场描述写死了结算细节，任何一条读错都会全盘错：

1. **必须用 T 组**：`T01390133` = 13.9°C（前 4 位是温度、后 4 位是露点）。无 T 组时退回正文 `18/12`（整度）。
2. **SPECI 不算**：只有 routine 报文计入，`SPECI` 开头的特殊观测明确排除。
3. **单位不统一**：美国站用 °F 档位（°C 换算后四舍五入，恰好 .5 进位），日/欧/亚站用 °C 档位。实测 NYC/LA/Seattle 是 °F，Tokyo/Shanghai/Paris/Munich 是 °C。**必须按市场自己声明的单位解析**。

已用官方四个算例逐一验证通过：

| °C | 官方应得 °F | 我的输出 |
|---|---|---|
| 18.3 | 65 | 65 ✓ |
| 17.8 | 64 | 64 ✓ |
| 19.0 | 66 | 66 ✓ |
| −22.5 | −8 | −8 ✓ |

### 4.4 "归零"的可执行路径（重要修正）

归零档位要"白拿钱"，现实路径是 **买入 NO**（付 `1−bid`，结算拿 1），而不是卖 YES——Polymarket 卖单需先持有份额。

实测镜像关系完全成立：

```
39°F 及以下：YES ask 0.001（232.9 份）|  NO bid 0.999  ← 完全镜像
44-45°F：   YES ask 0.47 / bid 0.40  |  NO ask 0.60 / bid 0.54
```

**但归零档位的 NO 卖单已经不存在**（YES 卖一已到 0.001，等价于 NO 买一 0.999）。这说明事件发生前，市场已经把低档位定价到接近零。**机会只存在于"新高刷新瞬间"的那几秒**，必须实时捕捉，事后回看永远看不到。

### 4.5 尚未拿到的数据

- **未观测到跨整点的归零事件**：录制期间 METAR 未刷新当日新高（各地当日高温多在上午已定型）。
- 正在跑 70 分钟录制覆盖 UTC 16:50–17:05 窗口，需等结果。
