# Phase 3 修正：收盘价列取错，首版结论作废

**日期**：2026-11-25
**触发**：接入实盘信号层时核对日线元组下标
**影响**：Phase 3 的**全部数字**（基线 1、基线 2、B&H、静态对照、门槛判定）
**不影响**：Phase 1（carry）、Phase 2 / 2B（截面）、15m 基线——它们用的是字典键取价，没有下标歧义

---

## 1. 问题

`research/lite/vol_target.py` 的 `load_daily()` 返回五元组：

```python
days.append((d, o, h, l, c))     # 索引 3 = low，索引 4 = close
```

但该模块里所有消费者都按 **索引 3 = 收盘价** 取值：

```python
run_baseline1:  rets = btc[i][3] / btc[i-1][3] - 1
run_baseline2:  series[s][i][3] / series[s][i-1][3] - 1
run_bh:         series[s][i][3] / series[s][i][1] - 1
```

于是整个 Phase 3 跑的是「**用每天的最低价当作收盘价**」的序列。
`align()` 里的注释 `# (o, c)` 恰好说明了原意——作者以为索引 3 是 close，
元组构造顺序和读取约定对不上。

这不是参数问题，是数据管道问题。修正方式是把元组改成
`(day, open, high, close, low)`，索引 3 统一为收盘价，并在 docstring 里写死。

原因：最低价序列的波动被放大、且系统性偏低（每日低点相对前一日低点的比值，
比收盘价比值更抖、均值更低）。策略的仓位缩放对波动敏感，放大的 σ 让仓位长期偏低，
而放大的噪声又让回撤看起来更小。**两个方向同时美化**。

## 3. 修正后的真实结论

| 组合 | 年化 | 夏普 | 最大回撤 | 卡玛 |
|---|---|---|---|---|
| BTC B&H | **+13.34%** | **0.500** | 52.97% | **0.252** |
| 静态 BTC @72.7%（同平均仓位） | +11.92% | 0.500 | **41.29%** | 0.289 |
| 基线 1 BTC vol-target | +6.87% | 0.366 | 46.27% | 0.148 |
| 基线 2 三币 RP+VT | +3.27% | 0.266 | 49.84% | 0.066 |

**六条门槛全部 FAIL，不只是原来那两条。**

更关键的是第三行与第二行的对比：

- 首版说「动态比静态同仓位好 +7.36pp 收益、+0.187 夏普、−3.19pp 回撤」
- 修正后是「动态比静态同仓位**差 −5.05pp 收益、−0.134 夏普、+4.98pp 回撤**」

也就是说，**波动率目标在这段样本里是负价值**，而不是"有效的风控工具但没提升夏普"。
原来准备新增的 `PARTIAL` 档在这组数据上没有适用对象。

机制上说得通：BTC 的波动聚集让 vol-target 在波动抬升后减仓（卖在低点）、
在波动回落后加仓（买在高点），趋势市里被双向磨损。静态 72.7% 的夏普恒等于满仓 B&H
（0.500 = 0.500），这是数学必然；动态版连这个基准都没跑赢。

样本外同样如此：

| 组合 | OOS 年化 | OOS 夏普 | OOS 回撤 |
|---|---|---|---|
| BTC B&H | −32.26% | −0.658 | 39.53% |
| 静态 @72.7% | −23.18% | −0.658 | **29.83%** |
| 基线 1 | −25.03% | −0.723 | 34.55% |

基线 1 在熊市里同样不如"期初买 72.7%、之后不动"。

1. **Phase 3 的台账结论仍记为 FALSIFIED**，但理由从"差 1.33pp 没到门槛"改为
   "全部门槛未过，且被同仓位静态基准全面压制"。

   该前提已被证伪。基础设施（信号层 + 运行器 + 自检 + 冻结演练）已就绪并通过验证，
   等下一个有正期望的候选再挂。
3. 首版报告 `phase3_verdict_2026-11-25.md` 与 JSON `phase3_1795594517.json` **保留不动**，
   作为审计痕迹；本文件是其更正，优先级更高。
4. 修正只改了数据管道的下标约定，**契约 `7ae39d11…` 未改，门槛未改，样本切分未改**。
