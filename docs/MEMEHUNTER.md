# MemeHunter（E 账户）— Solana meme 币虚拟盘

一个独立的、可审计的 **虚拟** 交易实验：由程序自己在 Solana 上挑选 meme 币标的，按信号到达时刻的真实报价模拟成交，不接钱包、不签名、不发任何真实订单。

它和 A/B/C（均线策略）、D（链上跟单）完全隔离：**自己的 SQLite 账本、自己的 1,000 USDT、自己的退出规则**，不进 Git，不并入任何合计权益。

---

## 1. 它为什么存在

A/B/C 的设计是「等指标成立」，BTC 在均线下方时几个月不开一单——这是正确行为，但也意味着**无法在短时间内观察到策略的期望收益**。D 的设计是「跟钱包」，回放已经证明在 24 bps 往返成本下是负期望（0/34 钱包为正）。

E 换一个方向：**给定一个必须自己做多空判断的资产类别，程序能不能在扣掉成本后取得正期望**。meme 币的特点是标的极多、淘汰率极高、成本结构极差，因此它是一个检验「研究流程本身是否可靠」的严苛场地。

## 2. 数据源

全部来自 Jupiter 公开 API（`lite-api.jup.ag`），无需 key、无需钱包：

| 端点 | 用途 |
| --- | --- |
| `/tokens/v2/toporganicscore/1h` | 主流按「有机分」排名的代币 |
| `/tokens/v2/toporganicscore/5m` | 5 分钟窗口的活跃代币 |
| `/tokens/v2/toporganicscore/24h` | 24 小时窗口，覆盖稳健型标的 |
| `/tokens/v2/recent` | 新池子（尚未被评分榜覆盖） |
| `/price/v3?ids=…` | 持仓的实时报价，用于标记与退出判定 |

四个榜单去重后约 100–150 个代币/轮。

**关键字段**（也是选择 Jupiter 而不是 DexScreener 的原因）：

- `organicScore` + `stats{5m,1h}` 的 `buyOrganicVolume` / `sellOrganicVolume`：区分真实成交与刷量。
- `audit.mintAuthorityDisabled` / `freezeAuthorityDisabled`：合约权限是否撤销。
- `audit.topHoldersPercentage`、`holderCount`：筹码集中度与持币广度。
- `liquidity`、`fdv`、`stats1h.buyVolume`。

## 3. 两段式筛选：否决 + 打分

早期版本用「全部条件必须同时通过」，实测 88 个代币里 0 个合格——因为 meme 币绝大多数天生残缺，十个条件的合取必然选不出东西。现在改成真实交易的做法：

### 3.1 一票否决（只拦会导致本金归零的条件）

| 代码 | 条件 | 为什么是绝对条件 |
| --- | --- | --- |
| `AUTHORITY_NOT_REVOKED` | mint 或 freeze 权限未撤销 | 供应可被增发、持仓可被冻结，无法通过任何交易纪律规避 |
| `HOLDERS_TOO_CONCENTRATED` | 前十大持有 > 55% | rug 的标准执行方式 |
| `TOO_FEW_HOLDERS` | 持币 < 300 | 新盘，无退出深度 |
| `LIQUIDITY_TOO_THIN` | 流动性 < 40,000 USD | 100 USDT 的仓位已经能吃出可观滑点 |
| `NO_LIQUIDITY_FLOW` | 1h 成交额 < 20,000 USD | 没有成交 = 没有对手盘，报价无意义 |
| `TOO_LARGE_TO_BE_MEME` | FDV > 8,000 万 | 蓝筹币的 5 分钟波动是噪声，不是 meme 行情 |
| `VOLUME_IS_WASH_TRADED` | 有机成交占 1h 总量 < 10% | 见下 |
| `NO_ORGANIC_DATA` | 有成交量但无有机成交数据 | 无法判断是真实需求还是刷量，缺证据不敢买 |
| `COLLAPSING` | 5 分钟跌幅 ≥ 12% | 正在崩盘中，不是回调 |

`VOLUME_IS_WASH_TRADED` 是实测出来的：`baton` 的 `organicScore` 是 60（"medium"），但它的有机成交量只占 1 小时总量的 **2.2%**。**标签和真实成交不一致，此时要信占比而不是信标签。**

### 3.2 打分（0–100，越高质量越好）

| 组成 | 上限 | 含义 |
| --- | --- | --- |
| `organic` | 30 | 有机分本身 |
| `pressure` | 25 | 1h 有机买/卖比，(ratio−1)×18 |
| `activity` | 12 | 1h 成交额 / 25,000 |
| `depth` | 8 | 流动性 / 50,000 |
| `breadth` | 15 | 持币人数 / 1,500 |
| `momentum` | 10 | 5m×1.5 + 1h×0.15 |

惩罚项：1h 涨幅 > 55%（追高）−20；5m 下跌 −(跌%×0.8)，上限 −8；有机卖压占优 −12；5m 净买家 ≤ 0 −10；1h 有机买额 < 3,000 −10；**筹码集中度超过 25% 后每 1% 扣 0.5，上限 −15**。

分数 ≥ `min_score_to_buy`（默认 52）才可下单。

两处修正值得记下来，因为它们都是「看起来合理但方向反了」的设计错误：

1. **`activity` 原本是「成交额 / 流动性」的比值**。比值让 $45k 的池子比 $400k 的池子得分更高——即程序偏好自己出不掉的场地。改成绝对成交额 + 独立深度项后，方向才对。
2. **5 分钟跌幅原本是一刀切 −15 分**。同一个代币（swordcat）在 4 分钟内从 59.5 掉到 44.5，只因 5m 涨跌幅从 −2.93% 变成 −4.27%。这不是严格，是把买入决定交给了扫描时刻。改成分级惩罚 + 12% 崩塌否决。

## 4. 成交与记账模型

- **仓位规模**：每仓 100 USDT，最多 5 仓，同一标的冷却 45 分钟。
- **成交价**：发现时刻的 Jupiter 报价 ×(1 + 滑点)，滑点由 `notional / liquidity` 估算，不低于 30 bps。**不是**被跟踪对象的成交价——我们不跟单。
- **成本**：往返 120 bps（手续费 + 点差），开仓扣一半、平仓扣一半。这是主动设定的偏保守假设。
- **现金**：开仓时 `名义 + 开仓费` 一次性从现金扣除；平仓时 `数量×成交价 − 平仓费` 回到现金。权益 = 现金 + 持仓按最新标记的市值。
- **失败处理**：取不到报价时**不平仓也不猜价**，下一轮再试；`mark_price` 缺失的仓位不计入退出判定。

### 退出规则（每轮 `update` 检查）

| 原因 | 条件 |
| --- | --- |
| `TAKE_PROFIT` | 浮盈 ≥ +55% |
| `STOP_LOSS` | 浮亏 ≤ −22% |
| `TRAILING_STOP` | 曾盈利，且从峰值回落 ≥ 30% 但仍为正 |
| `TIMEOUT` | 持有 ≥ 180 分钟 |

**重要**：退出判定只在轮次运行时发生。程序不跑，止盈止损不会触发——这是虚拟盘和真实系统共同的风险，账本里会留下「持有时间远超设计超时」的记录，这是停机证据，不是策略绩效。

## 5. CLI

```bash
python scripts/memehunter.py scan           # 扫描 + 建仓
python scripts/memehunter.py scan --dry-run # 只看候选，不建仓
python scripts/memehunter.py update         # 标记持仓 + 检查退出
python scripts/memehunter.py status         # 账户、持仓、权益
python scripts/memehunter.py candidates     # 最近一轮全部候选与否决原因
```

账本：`runtime/memehunter/memehunter.sqlite`（不进 Git，`.gitignore` 已排除）。

## 6. 已知缺陷（不掩盖）

1. **样本极窄**：约 100 个代币里，通常只有 0–5 个通过否决，过分数线的往往只有 1 个。这意味着每轮最多 1 笔，实盘节奏是「几十分钟一笔」，不是高频。
2. **无历史数据**：Jupiter 不提供历史 K 线，所以无法回测，只能前向观察。所有结论都建立在「从现在开始跑」的样本上。
3. **1h 有机买/卖比为 99 时含义模糊**：分母为 0 表示该窗口内没有有机卖出，可能是买盘极强，也可能是样本太小。这一点没有解决，只能在打分里按上限封顶。
4. **`mark_price` 来自 Jupiter 报价，不是可成交价**：对小市值代币，标记价与真实退出价之间还有一笔隐含滑点。退出成本里已含 60 bps，但可能仍偏乐观。
5. **进程存活**：受当前环境限制，轮次需要外部驱动才能持续；否则只在我触发时运行。
